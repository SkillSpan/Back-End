### The three identifiers, now distinct on every row

```
composite_algorithm_version = composite-readiness-v1   # STRUCTURE (which parts / how they aggregate)
configuration_version       = config-v{n}              # NUMBERS  (weights, cap, band thresholds)
algorithm_version           = skill-match-v1           # FastAPI's component algorithm
```

Rule: tuning a weight/cap/band bumps `config-*` only. Adding a component or changing the
exclusion/redistribution policy bumps `composite-readiness-*`.

  Laravel's Composite never calls it, so its 60.0 cap cannot conflict with Laravel's 69.0.

### Two gotchas discovered

1. **`effective_weights` is NOT on the audit snapshot.** There are two snapshots per calculation:
   `DecisionSnapshot.snapshot` (flow, payload, fastapi_result, version triple, `component_versions`)
   vs `ReadinessResult.snapshot` (adds `components`, `missing_component_policy`, `formula` with
   `effective_weights`, `critical_skill_rule`). Reading §5.1 data off the wrong one yields `null`.
2. **`critical_skill_gap_count = 0` is CORRECT here, not a bug.** A "critical gap" means a critical
   skill whose `match_ratio < minimum_match (0.50)` — not "a critical skill that isn't fully met".
   SQL (0.625) and Python (0.875) are both `partial` yet both above 0.50, so the 69.0 cap is
   rightly not applied.

### The two contracts differ in a way that matters

| | `/api/v1/skill-match` (Readiness) | `/api/v1/skill-gap` (Intelligence) |
|---|---|---|
| `critical_skill_*` fields | **ABSENT** | **PRESENT** (`cap_applied`, `readiness_cap`, `gap_count`, `ids`, `names`) |
| `weight_configuration_version` | present (`career-role-config-v1`) | **ABSENT** |
| top-level keys | 17 | 17 (different set) |

So the `critical_skill_*` ownership split is real and live-verified in **both** directions:
Laravel owns it on the Readiness path (the service sends nothing), while on the Intelligence path
the service owns it and `IntelligencePersistenceService` reads `critical_skill_cap_applied`
straight from the response — which is defensible there, since `skill-gap-v1` is that service's own
algorithm.

⚠️ **`critical_skill_readiness_cap` is present but `null` when the cap is not applied.** The key
exists, so a naive `?? 60.0` would fabricate a cap. Treat null as "not applied".

`critical_skill_gap_count` was **0** while two critical skills had non-zero level gaps — because
the criterion is the match **ratio** (`< 0.50`), not "gap > 0". Same semantics as the Readiness
flow's `minimum_match`. Consistent between the two contracts.

### Replay-data asymmetry (by design, worth knowing)

`ReadinessResult.snapshot` on the Intelligence path stores only
`decision_uuid, fastapi_skill_gap, fastapi_result, request_id` — no `formula`, no
`component_versions`. Correct: that flow does no local aggregation, so there is nothing to replay.
The §5.1 replay block belongs to the Composite flow alone.

Also: `skill_match_component` on the Intelligence row is populated from
`base_readiness_score` (not a skill-match score) — a naming carry-over, not a bug.

## Render deploy broke: port-scan timeout — root cause was stdout, not code

The push went through (`origin/feature/authentication` = `9341370`), and the Render deploy
that followed failed:

```
INFO  Nothing to migrate.
INFO  Configuration cached successfully.
==> Port scan timeout reached, no open ports detected.
```

**Root cause: `601c1f5` removed the seed-output redirect.** That commit was titled
"chore: surface seed output in Render logs for debugging" and changed

```
(php artisan db:seed --force > /var/log/seed.log 2>&1 &)     # worked
(php artisan db:seed --force &)                              # broke
```

**The redirect is load-bearing, not cosmetic.** `UniversitySeeder` upserts 10,000+ rows
(637 KB snapshot, chunked at 500) against a REMOTE database on every boot. Writing that
much text into Render's log pipeline keeps the single vCPU busy long enough that
`php artisan serve` misses Render's port-scan window.

This is the *same* failure the redirect was added to fix — `16af3ef`, titled
"fix: unblock Render deploy by starting server before seeding". So it regressed once and
was re-broken by a "visibility" tweak. **Never let a background job write to stdout in
this container.**

Mechanism note: `ServeCommand` prints `"Server running on..."` from `handleProcessOutput()`
(line ~319), i.e. *after* `startProcess()` — so the banner is a poor readiness signal.

### Fix — commit `98fbe8c`

```dockerfile
CMD php artisan migrate --force \
    && php artisan config:cache \
    && (php artisan db:seed --force > /var/log/seed.log 2>&1 &) \
    && exec php artisan serve --host=0.0.0.0 --port=${PORT:-10000}
```

`exec` added so the server replaces the shell and becomes PID 1, receiving Render's SIGTERM
directly. Verified locally that `a && b && (c &) && exec d` reaches `d` and that `exec`
really does keep the same PID.

### Ruled OUT as the cause (so nobody chases it again)

`Class App\OpenApi\OpenApiSpec ... does not comply with psr-4 autoloading standard ... Skipping.`

It is a **red herring**. The class lives at `app/OpenApi/app/OpenApi/OpenApiSpec.php` (a
doubled directory — a real misplacement) so Composer's optimized classmap skips it, but
`grep -rn OpenApiSpec app/ routes/ config/ bootstrap/` finds **zero references** — it is
documentation-only (for the `vendor/bin/openapi` tool). It cannot cause a boot failure, and
`php artisan migrate` / `config:cache` booted fine right before the timeout. Worth fixing
separately; not a deploy blocker.

recorded only the literal string `'Intelligence server error'`. FastAPI's `detail` — the one

never had this problem; it passes `safeJson($response)` as context.)
