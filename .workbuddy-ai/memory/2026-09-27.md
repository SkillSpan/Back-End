## Codebase analysis for mentor/student/project/communication features

Analyzed entire codebase in preparation for implementing mentor authentication,
student retrieval, project connection, conversation/messaging, chatbot endpoints,
notifications, and audit logging.

### Key findings

- **No "mentor" role** in roles table. ProfessionalProfile has `type` enum with
  `mentor` as a value + `verification_status` (pending/verified/rejected).
  Mentor auth/authorization must bridge Role + ProfessionalProfile.
- **No conversation/message/chat models or migrations exist** — all new.
- **AuditEvent** model + migration exist but zero `AuditEvent::create()` calls in
  app code. Infrastructure is there but unused.
- **Notification** model + migration exist with `event_key` uniqueness + `read_at`.
  Also used via Laravel Notification facade (mail channel) for OTP/password reset.
- **Project** has full lifecycle (draft→open→in_progress→completed), eligibility
  constraints (location/language/schedule/work_mode), applications with unique
  [project_id, applicant_id], teams→team_members.
- **StudentProfile** has `visibility` (public/organization_only/private) and
  `consent_given` — directly relevant to student visibility validation.
- **Middleware pattern**: `auth:sanctum` + `account.active` + `role:{slug}`.
  Role middleware uses `EnsureUserHasRole` which checks `$user->hasRole($slug)`.
- **Controller pattern**: thin Controller → Service → FormRequest. API Resources
  (JsonResource) for output. Custom exceptions with `status`, `codeName`, `details`.
- **X-Request-ID** correlation in every response header.

### What needs to be built

1. `mentor_student_connections` migration + model (mentor_id, student_id,
   project_id, status, audit fields)
2. `conversations` migration + model (connection_id, status, retention metadata)
3. `messages` migration + model (conversation_id, sender_id, body, metadata,
   read_at, soft deletes for retention)
4. `chatbot_interactions` (or reuse existing AssistantInteraction pattern)
5. Middleware or policy for mentor authorization
6. Controllers, services, form requests, API resources
7. Active audit logging via AuditEvent::create() at key state transitions
8. Notification dispatch via existing Notification model at connection/message events
9. Comprehensive feature tests covering all listed scenarios

### Patterns to follow

- Migrations: additive + idempotent (`if (! Schema::hasColumn(...))`)
- Tests: RefreshDatabase, role seeding in setUp(), postJson() assertions
- Error responses: `code` + `message` + `request_id` JSON shape, 401/403/422/404

## Gap closure — notifications API + chatbot endpoints

Audited the user's full task list against the implementation and found two
requirements not yet covered: "Relevant notifications" (API) and "Implement
chatbot communication endpoints". Built both.

### Notification API (new)
- `app/Services/NotificationService.php` — central dispatch gateway:
  - `dispatch()` honours `notification_preferences` (opt-out: no row = enabled)
    and is idempotent on `event_key` (returns null on re-dispatch).
  - `list()` (category + unread_only filters, paginated), `unreadCount()`,
    `markAsRead()` (owner-scoped), `markAllAsRead()`, `isEnabled()`,
    `getPreferences()`, `setPreference()` (upsert).
- `app/Http/Controllers/Api/NotificationController.php` + `NotificationResource`
  + `UpdateNotificationPreferenceRequest`.
- Routes under `auth:sanctum` + `account.active`: `GET /notifications`,
  `GET /notifications/unread-count`, `POST /notifications/read-all`,
  `GET|PUT /notifications/preferences`, `POST /notifications/{id}/read`.
- **Refactored** `MentorStudentService` + `ConversationService` to route all
  notification creation through `NotificationService::dispatch()` so user
  preferences are actually respected (they previously called
  `Notification::create()` directly, bypassing preferences).

### Chatbot endpoints (new)
- `ConversationService::sendChatbotMessage()` — forces `message_type=chatbot`,
  merges `source` into metadata, writes distinct audit action
  `chatbot.message.sent`, notifies the other participant.
- `ConversationService::getChatbotMessages()` — chatbot-only listing.
- `app/Http/Controllers/Api/ChatbotController.php` +
  `SendChatbotMessageRequest` (deliberately does NOT accept `message_type`, so a
  client cannot spoof a human 'text' message through the bot endpoint).
- Routes: `POST|GET /api/v1/conversations/{id}/chatbot/messages`.

### Bug found and fixed
- `Notification` model's `$fillable` omitted `read_at`, so
  `$notification->update(['read_at' => now()])` silently no-oped. Added
  `read_at` to fillable. (Query-builder `markAllAsRead` masked the bug because
  builder updates bypass mass-assignment.)

### New tests (40)
- `NotificationTest` (22): auth, listing/filters, unread count, mark-as-read
  (incl. 404 for another user's row, idempotency), mark-all-as-read, preferences
  CRUD + validation, **preference suppression actually blocking dispatch**,
  idempotent dispatch, X-Request-ID.
- `ChatbotTest` (18): auth, posting (mentor/student), message_type spoofing
  blocked, source metadata, non-participant 403, archived 422, body required,
  length cap, distinct audit action, notification, retrieval isolation from

## End-to-end verification of the Postman collection (newman)

Ran the collection for real via **newman** against an **isolated local SQLite
instance** — never against the remote Clever Cloud MySQL in `.env`.

### Result
**23 requests / 24 assertions / 0 failures**, ~17s.

### Reusable harness recipe (the remote DB must NOT be touched)
1. `touch database/postman_test.sqlite`
2. `DB_CONNECTION=sqlite DB_DATABASE="<abs path>" php artisan migrate --force`
3. Seed a verified mentor + public student + open project (temp script), then delete it
4. `DB_CONNECTION=sqlite DB_DATABASE="<abs path>" php artisan serve --host=127.0.0.1 --port=8000`
5. newman lives in the isolated workspace:
   `C:\Users\HP\.workbuddy-ai\binaries\node\workspace\node_modules\newman\bin\newman.js`
   run it with the managed node and `--env-var "base_url=http://127.0.0.1:8000"`
   (environment vars outrank collection variables in Postman precedence).

### Gotchas hit (both cost a debugging round)
- **`Model::query()->delete()` is a SOFT delete on models using SoftDeletes**
  (`User`, `Message`, `Conversation`, `MentorStudentConnection`). The rows survive
  and unique keys collide on re-seed. Use raw `DB::table(...)->delete()` in
  FK-safe order for a hard reset.
- **SQLite AUTOINCREMENT counters persist** across deletes, so IDs drift
  (mentor 3/student 4 instead of 1/2) and stop matching the collection defaults.
  Fix: `DB::table('sqlite_sequence')->delete()` (guarded — the table only exists
  once an AUTOINCREMENT row has been written).

### Collection bug found by the run
The notification folder originally ran as the **mentor**, whose notification list is
always empty (the mentor is the actor, the student is the recipient) → `notification_id`
never captured → `POST /notifications/1/read` returned 404. That 404 was the ownership
guard working correctly, not a defect. Fixed by adding a **student-login step at the
top of folder 4** that swaps `{{token}}`, plus `student_email` / `student_password`
collection variables. Now the folder exercises the real receiving side.

### Suppression proven end-to-end (beyond the collection)
After the collection disabled the student's `message`/`in_app` preference:
student unread count stayed **0 → 0** while the mentor's message still returned
**201** and landed as the conversation's last message. Message delivered,
notification suppressed — exactly the intended contract.

### Cleanup
Deleted `_postman_seed.php` and `database/postman_test.sqlite`. Only the collection
file remains as the deliverable.

## Committed the collection — and hit the git gotcha hard

Committed `postman_mentor_communication.json` as `e395541`
("docs(api): add verified Postman collection for mentor/student communication").

Found the mentor work was already committed earlier in `6a1c1a9`
("fetaure : add mentor in stage", 38 files / 5131 insertions) — nothing was lost.

**The git gotcha bit twice, and the real trigger was misdiagnosed before:**

- The ref `refs/heads/feature/authentication` sits in a *nested* directory.
  `git commit` deletes that directory — but only *after* the commit succeeds, so
  the commit itself is fine; you just re-write the ref with the NEW sha.
- **`git reset` is far worse and is the actual landmine.** It deletes the ref
  *before* doing anything, so every subsequent git command reports
  "does not have any commits yet" and stages the whole repo as new. My first
  attempt at committing died this way because I opened with `git reset -q`.
- `git update-ref` returns exit 0 but does **not** persist the ref here. Only
  `mkdir -p` + `printf` works.
- `core.logAllRefUpdates=false` → no reflog, so recovery needs the SHA from
  memory/the commit output.

Recovered twice: first to `3270346` (HEAD before the damage), then to `e395541`
after the successful commit. `git read-tree HEAD` was used to reset the polluted
index without touching refs. Full playbook now written into `MEMORY.md`.

**Lesson for next time:** never `git reset` on this checkout; verify
`.git/refs/heads/feature/authentication` exists after every git write.

## `POST /api/v1/setup/create-mentor` (shared-secret mentor bootstrap)

Added `createMentor()` to `SetupController` mirroring `createAdmin()`, route
`throttle:10,1`, `services.mentor_setup.secret` (`MENTOR_SETUP_SECRET`), and
`tests/Feature/Auth/SetupCreateMentorTest.php` (9 tests / 69 assertions).
Suite went 419/1444 → **428/1513**, Pint clean.

**Real bug found in the requested spec — `verification_status` is NOT in
`ProfessionalProfile::$fillable`.** The spec said to use
`updateOrCreate(['user_id'=>$id], ['verification_status'=>'verified', ...])`,
which mass-assigns and therefore *silently drops* the value: the column stayed
at its `pending` default and the JSON response returned `null`. Proven by
temporarily restoring the spec version — the happy-path test failed with
`Failed asserting that null is identical to 'verified'`.

Fix: `firstOrNew(['user_id' => $id])` + `fill([...safe...])` + explicit
`$profile->verification_status = 'verified'` + `save()`.

**Do NOT "fix" this by adding `verification_status` to `$fillable`.**
`EnsureUserIsMentor` gates every mentor endpoint on that exact column, so
making it mass-assignable turns any future `create($request->all())` into
self-promotion to verified mentor. The sibling model `SkillEvidence` *does*
list it in `$fillable`, and the existing comms tests use
`ProfessionalProfile::forceCreate(...)` to bypass the guard — that pattern is
deliberate, not an oversight.

Live-verified end to end on an isolated SQLite DB (`APP_ENV=local`, env
overrides beat `.env` because Laravel's Dotenv uses immutable `safeLoad`):
persisted row `type=mentor status=verified`, `User::count()` unchanged at 2
(no second account), suspended user → 422, and the promoted user's token got
**200** on `GET /api/v1/mentor/students` — proof the privileged column really
landed.

**Never run `migrate`/`serve`/`tinker` here without first overriding
`DB_CONNECTION`/`DB_DATABASE`** — the checked-in `.env` points at the live
Clever Cloud MySQL with `APP_ENV=production`.

Postman collection grew to 26 requests: new folder `5 · Setup (create-mentor)`
(3 requests, 8 assertions, 0 failures via newman), plus `mentor_setup_secret`
and `professional_profile_id` collection variables. Kept as the last folder so
the existing 23-request green flow is unaffected.

## create-mentor reworked: it now REGISTERS the mentor (supersedes above)

**User directive (explicit):** "يسجل وخلص بدون تحقق ... لانو انا فقط الي كون
مسؤول عن تسجيل المنتور" — the endpoint must create the account outright. The
original "promote an existing user only" spec is dead. Reason: the only way to
get an `active` user was `/auth/register` → `/auth/verify`, and the OTP is
delivered by **real SMTP (Brevo)**, so a Postman-only onboarding was impossible.

New behaviour of `SetupController@createMentor`:

| Email state | Result |
|---|---|
| not found | creates user, `status=active`, `email_verified_at=now()`, `registered=true` |
| exists, `active` | promotes, `registered=false` |
| exists, `pending` | activates + promotes (secret holder vouches) |
| exists, `suspended`/`deleted` | 422 |
| soft-deleted | 422 |

Other changes: dropped the `exists:users,email` rule; added nullable `name`
(falls back to the email local-part) and nullable `password` (`min:8`). A
**generated** password is returned once as `data.generated_password`; a
caller-supplied one is never echoed. Response gained `registered`, `status`,
`name`. Route/throttle unchanged.

**Second real bug caught:** without `User::withTrashed()` the soft-deleted case
returns **500 `UNIQUE constraint failed: users.email`** — a soft-deleted row
still owns the unique index, so the model-scoped lookup returned null and
`forceCreate()` then collided. Proven by removing `withTrashed()` and watching
the test fail with that exact SQL error. Regression test:
`test_rejects_a_soft_deleted_account_instead_of_crashing`.

Tests rewritten: 13 tests / 103 assertions, incl. the strongest one —
`test_newly_registered_mentor_can_reach_the_mentor_endpoints` (register → login
with the generated password → `GET /api/v1/mentor/students` 200). Suite:
428/1513 → **432/1547**. Pint clean.

Live-verified from an **empty** DB: newman folder 5 = 3 requests / 11 assertions
/ 0 failures; DB showed 2 users both `active` + verified; and a curl run did
register (`name=brand.new` derived, 16-char password) → login → mentor endpoint
**200**. Collection updated: folder 5 is now `تسجيل مرشد جديد (إيميل جديد)`
(email auto-generated via `Date.now()` in a pre-request script, so it always
asserts `registered=true`), `تسجيل/ترقية إيميل موجود`, `سر غلط (لازم 403)`.
The old "unknown email → 422" request was **deleted** — that behaviour is gone.

**Open question flagged to the user:** the new user gets **no role** (mentor
identity is the ProfessionalProfile, per the existing architecture). If mentors
also need the `learner` role for some endpoints, that still has to be added.

## create-mentor doubles as the admin's password-reset path

**User directive:** "رح سجلوا وهو يسجل دخول عادي بس ممكن ينسى الباسورد فانا نفسي
بروح في api" — the admin registers the mentor, the mentor logs in normally, and
if the mentor forgets the password the ADMIN fixes it through the API. The
mentor must not be required to have inbox access.

Note: a full OTP password-reset flow **already existed** and needed no work —
`/api/v1/auth/forgot-password` → 6-digit code by email (10 min) →
`/forgot-password/verify` → `/reset-password`. But that mails the code to the
MENTOR's address, which is exactly the thing the admin may not control, so it
does not solve this case.

Change: on an **existing** user, a supplied `password` is now applied
(`password_reset: true` in the response). Omitting it deliberately leaves the
old password alone — it must NOT silently mint a random one. Implemented as a
single `$updates` array + one `forceFill()->save()` covering the pending→active
flip and the password together.

Live-verified end to end: register → generated password → login 200 → re-call
with a new password (`password_reset=true`) → new password login **200** →
wrong password **422** (`The provided credentials are incorrect.`).

Tests: 15 / 121 assertions. Suite 432/1547 → **434/1565**. Pint clean (it
wanted a real `use Illuminate\Support\Facades\Hash;` import instead of the
inline FQN — run `pint` not just `--test` when adding assertions).

Postman folder 5 is now 4 numbered requests (run in order 1→4): register new,
register/promote existing, **reset password** (targets the throwaway account
from step 1 so it never touches the user's real login), wrong secret. The reset
request's `password_reset` assertion is conditional on `registered === false` so
it stays honest when run standalone. Collection: 27 requests total.
Live newman: 4 requests / 14 assertions / 0 failures.
