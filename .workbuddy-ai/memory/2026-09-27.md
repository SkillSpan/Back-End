## Finalization pass (Tasks A–F)

### Task A — snapshot integrity (the real fix)
`baseline_question_snapshots` had `cascadeOnDelete()` on `baseline_assessment_item_id` AND `skill_id`, so deleting a bank question or a skill **destroyed assessment history**. New migration `2026_09_28_000006_protect_baseline_snapshot_integrity`:
- `baseline_assessment_item_id` → nullable + `ON DELETE SET NULL` (snapshot detaches; frozen content keeps it readable/submittable).
- `skill_id` → `ON DELETE RESTRICT` (refuse the delete; don't orphan).
- `baseline_assessment_id` + `career_role_id` keep CASCADE (parent owns its snapshots).
- **Dropped `bqs_assessment_item_unique`** — with nullable item refs, NULLs stop colliding so the index would silently enforce nothing.
- SQLite can't ALTER an FK in place; the driver rebuilds the table. Verified via `PRAGMA foreign_key_list` in tests.

## Gap closure — notifications API + chatbot endpoints

Audited the user's full task list against the implementation and found two
requirements not yet covered: "Relevant notifications" (API) and "Implement
chatbot communication endpoints". Built both.

### Notification API (new)
- `app/Services/NotificationService.php` — central dispatch gateway:
  - `dispatch()` honours `notification_preferences` (opt-out: no row = enabled)
    and is idempotent on `event_key` (returns null on re-dispatch).
  - `list()` (category + unread_only filters, paginated), `unreadCount()`,
    `markAsRead()` (owner-scoped), `markAllAsRead()`, `isEnabled()`,
    `getPreferences()`, `setPreference()` (upsert).
- `app/Http/Controllers/Api/NotificationController.php` + `NotificationResource`
  + `UpdateNotificationPreferenceRequest`.
- Routes under `auth:sanctum` + `account.active`: `GET /notifications`,
  `GET /notifications/unread-count`, `POST /notifications/read-all`,
  `GET|PUT /notifications/preferences`, `POST /notifications/{id}/read`.
- **Refactored** `MentorStudentService` + `ConversationService` to route all
  notification creation through `NotificationService::dispatch()` so user
  preferences are actually respected (they previously called
  `Notification::create()` directly, bypassing preferences).

### Chatbot endpoints (new)
- `ConversationService::sendChatbotMessage()` — forces `message_type=chatbot`,
  merges `source` into metadata, writes distinct audit action
  `chatbot.message.sent`, notifies the other participant.
- `ConversationService::getChatbotMessages()` — chatbot-only listing.
- `app/Http/Controllers/Api/ChatbotController.php` +
  `SendChatbotMessageRequest` (deliberately does NOT accept `message_type`, so a
  client cannot spoof a human 'text' message through the bot endpoint).
- Routes: `POST|GET /api/v1/conversations/{id}/chatbot/messages`.

### Bug found and fixed
- `Notification` model's `$fillable` omitted `read_at`, so
  `$notification->update(['read_at' => now()])` silently no-oped. Added
  `read_at` to fillable. (Query-builder `markAllAsRead` masked the bug because
  builder updates bypass mass-assignment.)
